# Addendum 2026-09-06 — onboarding UX audit (discomfort points)

Flow audited (committed HEAD code): register → /r/claim → /profile?onboarding=true →
/prediction → PremiumGate (free) / forced /taste (premium). Ordered by pain.

## High-discomfort

- **O1 — Silent bounce loop on incomplete submit.** Only First/Last Name carry `required`;
  birthday, sex, height, weight, activity (the fields the gate actually checks) do not.
  A partial submit returns 200, hard-navigates to /prediction, the onboarding gate bounces
  straight back to the same "Welcome!" form with **no message about what's missing**.
  `ProfileForm.tsx` (no required flags / no field validation) + `app/(dashboard)/layout.tsx` gate.
- **O2 — "Profile incomplete" shown to users whose profile IS complete.** `computePredictionEstimate`
  returns null for healthy-BMI users by design, but `PredictionView.tsx:63` renders the same
  "Profile incomplete" empty state for that null — the first screen after finishing onboarding
  calls the user's completed work incomplete and loops them back to the form.
- **O3 — API error messages never reach the user.** `handleSubmit` throws
  `new Error("Failed to save profile")` on any !ok — the API's specific 422 texts ("Birthday must
  be a valid past date (age 13–120)", height/weight ranges) and the 409 email-conflict
  "contact support" message are all swallowed into one generic banner. `ProfileForm.tsx:~170`.
- **O4 — Paywall surprise after the long health form (free users).** Marketing says "Start free";
  free tier is profile + prediction + membership only. A free user invests in the full health
  questionnaire, then every sidebar destination is the lock screen — including /overview,
  which is also the login landing (`fallbackRedirectUrl`), so every return visit opens on a paywall.
- **O5 — Premium users are trapped in Dish Tinder.** Every dashboard navigation redirects to
  /taste until all 10 dishes are swiped; there is no "skip for now" for the deck (only per-dish
  skip), and known bugs M8/M9 (swipe failure bricks the buttons; fetch error renders as success)
  sit inside this forced flow.

## Medium

- **O6 — Button label lies:** "Save & Continue to Meal Plan →" lands on /prediction (free) or the
  forced /taste redirect (premium) — never the meal plan.
- **O7 — The reward moment is invisible:** the live Estimated Caloric Summary never renders in the
  default ft/in unit (bug L16) — most US users fill the whole form with zero feedback.
- **O8 — lbs-only weight fields:** Weight and Goal Weight are hard-labeled "(lbs)" with no kg
  option (height has a full cm/in/ftin selector); goal-weight validation is hardcoded 50–1000 lbs.
  Metric users must hand-convert or get baffling range errors.
- **O9 — Sidebar visible but non-functional during onboarding:** every link boomerangs back to the
  form via the gate with no explanation of why.
- **O10 — Sensitive data with no reassurance:** sex at birth, weight, health conditions, allergies
  are collected with zero why-we-ask/privacy copy.
- **O11 — Clerk dev instance** (production blocker §1): sign-up/verification emails come from
  clerk.accounts.dev and sessions churn — "login every time" is itself onboarding discomfort.
- **O12 — /r/claim cold-start delay** on the sign-up hot path (no maxDuration; bug L25) — the
  pause happens at the exact moment of highest drop-off risk, right after "Create account".

## Minor

- O13 — No required-field indicators anywhere on the form; no progress/step indication on a
  4-section, 5-chip-group single page.
- O14 — Theme flip mid-flow: dark navy auth pages → light cream dashboard.
- O15 — Emoji as icons in taste states (🍽 ✅ 🎉 🧠) vs the SVG convention elsewhere.
- O16 — Sex options come straight from the `gender` table; any value besides Male/Female silently
  disables the preview and downstream engine (verify what the table actually contains).
- O17 — Extra visible redirect hop through /api/taste/set-cookie for pre-existing premium users.

Good bones worth keeping: the gate self-heals stale onboarding flags instead of trapping old
accounts; /r/claim is genuinely fail-safe (attribution can never break sign-up); portal-only
staff are never forced into patient onboarding; the pending-invite banner on /profile.
